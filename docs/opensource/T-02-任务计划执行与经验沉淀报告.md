## 1. 执行摘要

### 1.1 一句话结论

Vannevar **不是半成品，而是一个「实现完成度高、但收尾没做完、且文档与实现存在失真」的项目**。本批把三处真实缺口全部补齐、并把文档声称与实现完全对齐：

1. **Muse 的同步从明文改为端到端加密**（此前 README 声称它支持加密，实现里加密代码为零）；
2. **跨设备解密真正成立**（salt 作为公开参数上云，另一台设备用同一口令即可解密历史密文）；
3. **顺手修掉一个此前从未被发现的真实缺陷**——Muse 的 push 请求不带 `X-CSRF-Token`，而 Bridge 写端点强制校验该头，**Muse 的云同步在生产模式下必然 403**。

同时把 `docs/phase4-plan.md` 的未勾选验收项从 **12 项降到 0 项**（其中 11 项实为早已实现却从未回填，1 项本批才真正落地），并新增一道机器门禁防止共享层副本再次漂移。

### 4.2 ST-01：共享加密核心与双端薄封装

**核心实现**：`shared/vannevar-crypto.js` 导出 `createCryptoModule({storeKey, verificationPlaintext})` 工厂，返回 Focus 原有 API 的**同构**实现（9 个函数 + 本批新增 `getLocalProfile` / `adoptRemoteProfile`）。另导出 `createCryptoProfileSync({getAuthToken, getBridgeUrl, getBridgeHeaders, crypto})` 网络层（依赖注入，避免共享层绑定产品路径）与 `isValidProfile`。

**为什么是工厂而不是两份实现**：Focus 原有 `crypto.js` 里 `CRYPTO_STORE_KEY = 'vannevar_focus_crypto'` 与 `VERIFICATION_PLAINTEXT = 'vannevar-focus-e2e-verification-v1'` 是硬编码的；若直接复制到 Muse，两份 300 行加密代码会各自演化——**修一个加密漏洞要改两处**，这是比「半成品」更严重的隐患。工厂化后 Focus/Muse 共用同一份已验证实现。

**Focus 零回归的验证方式**：`products/focus-mvp/crypto.js` 改为薄封装后**导出签名与文件路径完全不变**，既有 `test_crypto.mjs`（16 条）与 `test_sync_crypto.mjs`（11 条）**一行未改**即通过——这是「重构不破坏既有契约」的直接证据，而非靠改测试凑绿。

**副本一致性**：三份文件 sha256 均为 `5B4CE9C622E8696EEACF301D6D8A772C1992265417FC5F86AFA39BF2F605BA2B`。

### 4.3 ST-02：Muse 接入加密（以及那个被顺带挖出来的真实缺陷）

Muse 侧改动：`core/sync.js`（push 加密 / pull 解密 / 未解锁抛错）、`core/auto-sync.js`（未解锁即跳过 + 通知节流）、`core/background.js`（`CRYPTO_UNLOCK` / `CRYPTO_LOCK` / `CRYPTO_DISABLE_SW` 消息通道）、`options/options.{html,js}`（加密配置区）。

**关键实现细节：**

1. **pull 侧兼容旧明文**：`decryptItemData()` 先判 `isEncryptedData()`，旧明文原样返回；密文解密失败（口令错 / 数据损坏）**跳过该条而非整体失败**——避免一条坏数据让整次拉取失败。
2. **uuid 映射补充的修正**：原代码用 `remoteItems.find(ri => ri.data.createdAt === insp.createdAt)` 匹配新导入记录，但密文条目的 `item.data.createdAt` **不可直读**。改为在解密阶段建立 `createdAtByUuid` 映射再匹配——否则密文条目导入后**拿不到 client_uuid**，下次 push 会被当成新记录重复推送。
3. **mood 也加密**：氛围标签与灵感同属用户上下文，密文容器同样覆盖。

**⚠️ 顺带发现并修复的真实缺陷（F-14 / F-15）**：

查 Bridge 的写端点校验时发现 `auth.py:439-441` 明确要求 `X-CSRF-Token` 头等于 JWT 的 `csrf_jti`，否则 403。而 Muse 的 `core/sync.js` 的 push 与 pull **都只带了 `Authorization`**，没有该头；Focus 侧早在 `B-P1-3-e` 用例里锁死了这个契约，Muse 侧没有对应用例。

推论：**Muse 的云同步在生产模式下必然 403**（dev 模式走 Basic Auth 降级，同样需要全局 CSRF 双重提交，扩展的跨源 fetch 也带不上 Cookie）。这解释了为什么 Muse 的同步功能长期没有暴露问题——它根本走不通。

处置：Muse 的 push / pull 统一改用 `getBridgeHeaders()`（该函数早就存在于 `muse-mvp/core/auth.js:187`，只是 `sync.js` 没用它），并新增用例锁死该契约。

### 4.4 ST-03：Bridge 加密档案后端

- 模型 `UserCryptoProfile`（`models.py`）：`user_id` 主键 + `salt` / `iterations` / `kdf` / `salt_fingerprint` / `verification_ciphertext` / `verification_nonce`。
- 迁移 `PRAGMA user_version` **v11 → v12**（`database.py`），幂等 `CREATE TABLE IF NOT EXISTS`。
- Schema `CryptoProfileIn` / `CryptoProfileOut` / `CryptoVerificationIn`（`schemas.py`），入参有长度与区间约束（`iterations` 1000 ~ 1,000,000）。
- 端点 `GET` / `PUT /api/auth/me/crypto-profile`（`routers/auth_router.py`），挂 `require_user`（JWT 写端点自动校验 per-session CSRF）。

**为什么用独立表而不是在 `users` 表加列**：档案与账号 1:1，但它是「加密元数据」而非「账号属性」，未来可能加版本号、轮换记录等字段；塞进 `users` 会让账号表持续膨胀，且与 `users.token_revoked_at` 这类「账号生命周期字段」混在一起语义不清。

**存储的到底是什么**：PBKDF2 **salt 是公开参数、不是密钥**——它的作用是让不同设备派生出同一把密钥，本身无法反推口令。档案里另存一份固定明文的**密文**（verification），用于在新设备上反验「你输入的口令对不对」。**口令本身永不落库、永不上行。**

### 4.5 ST-04：salt 上云与跨设备复用

**客户端流程**：

1. 启用加密时先 `GET` 云端档案：
   - 云端**已有**档案 → 复用其 salt 派生密钥，并用云端 verification **反验口令**；一致则本地沿用同一 salt（跨设备可解密），不一致则明确报错「passphrase 与其它设备不一致」。
   - 云端**无**档案 → 本地生成 salt + verification，并 `PUT` 上云。
2. 每次 push / pull 成功后**幂等** `PUT` 一次本地档案 —— 这一步让「老版本已在本地启用加密、但云端尚无档案」的用户**首次同步时自动补齐**，无需任何手动操作。
3. 云端档案与本地 salt **不一致**时，`ensureRemoteProfile()` **不覆盖**云端（覆盖会毁掉另一台设备的历史），只置「未同步」状态。

**跨设备解锁流程**（设置页）：本机已启用 → 用本地 salt 解锁；本机未启用（设备 B）→ 拉云端档案并 `adoptRemoteProfile(passphrase, remote)`，成功后把远端 salt 写入本地并装载密钥。

盲审共报出 **P0=0 / P1=3 / P2=6 / P3=9**。处置结果：**P1 全部处置（2 项修复 + 1 项明示边界）、P2 修 5 留 1、P3 修 5 留 4**。逐条见 §5.5.1，此处记录三处设计层面的处置。

#### 4.8.1 「不覆盖他人档案」从「客户端自觉」升级为「客户端 + 服务端双保险」

修复前，`pushRemoteProfile()` 无条件 PUT；服务端 `PUT /api/auth/me/crypto-profile` 也无条件赋值——**两端都把「覆盖」当成正常行为**。修复后：

- 客户端：`fetchRemoteProfile()` 改为**三态**（`ok` / `absent` / `error`），`pushRemoteProfile()` 在写入前先 GET 比对 salt；
  - 云端**确实没有**档案（404）→ 才写入；
  - 云端状态**未知**（网络 / 5xx / 鉴权失败）→ **拒绝写入**（宁可不同步，也不能赌云端是空的）；
  - 云端已有**不同** salt 的档案 → **拒绝写入**（那是别的设备的，覆盖会毁掉它的历史密文）。
- 服务端：salt 不同时返回 **409 `crypto_profile_conflict`**（纵深防御；客户端即使出错也不会毁掉他人档案）。
- 测试：新增 4 条用例（Muse 2 条 / Focus 2 条）分别锁死「状态未知不写」与「salt 不匹配不写」。

**这条不变量在修复前是零覆盖的**——盲审用一个「删掉守卫后全部测试仍绿」的变异证明了这一点。

#### 4.8.2 verification 明文跨产品统一：让「统一账号」真正统一

原设计让 Focus 与 Muse 各用各的 verification 明文（`vannevar-focus-…` / `vannevar-muse-…`），本意是产品隔离；但档案表按**账号**只有一行，于是：

> 同一账号先在 Focus 启用加密 → Muse 启用时拉到的是 Focus 的档案 → Muse 拿**自己的**明文去反验 Focus 的 verification → 必然失败 → **口令完全正确却被报成「与其它设备不一致」**。

修法是把 verification 明文改为跨产品统一的 `vannevar-e2e-verification-v1`。副作用是**正向的**：同一账号下 Focus 与 Muse 共享同一份档案（同一 salt、同一密钥），因此两者的密文可以互相解密——这恰好兑现了仓库「统一账号体系 + 跨产品上下文协同」的定位，而不是与它冲突。产品的**本地**存储仍然隔离（`vannevar_focus_crypto` / `vannevar_muse_crypto` 两个 storeKey 不变）。

#### 4.8.3 「端到端加密」的承诺边界：明示而不是假装

盲审指出：弹窗「推送到 Bridge 项目档案」走的是 `bridge-link.js`，与同步路径完全独立，**明文**上行 title / url / note / mood。

本批**有意不改实现**，理由是产品性的：Bridge 侧的 AI 交接摘要、统计热力图、项目详情页都依赖 `ProjectContextSnapshot` / `ProjectContextInspiration` 的**可读字段**；把它们加密会让这些功能失效。因此处置方式是**把边界讲清楚**——两端设置页的「Bridge 项目关联」卡片与根 README 的安全模型表都写明：

> 「数据同步」走端到端加密（Bridge 只存密文）；「推送到 Bridge 项目档案」**不加密** —— Bridge 需要读取标题、链接与摘要来生成交接摘要和统计图表。

把它记成一个待用户拍板的边界问题（§6.3），而不是默默留着。

## 8. 经验沉淀

### E-01 「文档里没写」与「文档写错」是两类缺陷，处置方式不同

- **写错**（CHANGELOG 声称 Muse 已加密，实现里加密代码为零）→ 必须**补实现**让声称成立，或改声称。
- **没写 / 措辞含混**（README 的「同步内容端到端加密（见上）」实指 Focus）→ 补**明确措辞**即可。
- 开工时的口头评估把二者混为一谈，还记错了行号。**文档缺陷必须逐条核到行号**，不能凭印象——口头结论一旦有偏差，会直接影响用户对问题严重性的判断。

### E-02 「共享层 + 产品副本」模式必然产生副本漂移，必须配机器门禁

- 实测：3 组共享副本中 **2 组已经漂移**（`brand.css` 差 117/166 行、Bridge 侧 `vannevar-shared.js` 差 242/197 行），且**漂移不报错**——只在运行时表现为「同样的功能在 A 产品能用、B 产品不能」。
- 纯靠人工同步必然遗漏。`check_shared_sync.py` 的价值不在于「现在一致」，而在于**以后不一致会立刻被挡住**。

### E-03 跨设备加密的分界线：公开参数可同步、秘密不可同步

- PBKDF2 **salt 是参数不是密钥**——它只影响派生速度，不影响安全性本身；上云它换来了「另一台设备能派生同一把密钥」。
- 派生密钥、口令、verification 明文**一律不上云**。
- 跨设备能力的关键不是「把密钥搬过去」，而是**让两边能自己算出同一把密钥**。

### E-04 可选安全功能必须 fail-closed，且每个写路径都要拦

- 「加密已启用但未解锁」这个状态（Service Worker 重启后必然出现）如果不处理，系统会**静默降级为明文推送**——用户以为数据是密文的。
- 拦截点必须覆盖 push、pull、自动同步三条路径，外加系统通知告知用户去解锁。

### E-05 修过的坑要同步到兄弟产品，并用用例锁死契约

- Focus 的 `B-P1-3-e` 用例锁死了「push 必须带 `X-CSRF-Token`」这个契约；Muse 侧修复同一个功能时**没有对应用例**，于是同类缺陷在 Muse 上长期存在且无人察觉。
- ⇒ **「修过的坑」应当沉淀为契约用例，而不是留在某个产品的测试里**。本批已为 Muse 补上同等用例。

### E-06 新增网络请求会污染既有测试的捕获变量

- 新增「push 后自动同步档案」的 PUT 请求后，Focus 既有测试里 `capturedBody = JSON.parse(opts.body)` 被档案请求覆盖 → 用例失败。
- 修法：在 `fetch` mock 入口按 URL 分流档案端点，而不是在每个用例里各写一遍。这也让「档案端点被调用了几次」成为可断言的事实。

### E-07 跨产品 pull 的过滤维度差异会静默吞掉测试数据

- Muse 的 pull 按 `item_type` 过滤条目，Focus 不过滤。同一份测试数据在 Focus 通过、在 Muse 导入数为 0。
- ⇒ **写跨产品测试时，要按各自实现核对过滤维度**，不能照搬兄弟产品的测试数据。

### E-08 「测试通过」不等于「功能可用」——真实服务端复核不可省

- 本批为跨设备链路额外起了一个真实 Bridge 实例，用两个独立模块实例走完整流程（真注册、真 JWT、真 CSRF、真档案 PUT/GET），9/9 通过。
- 单测里的 mock 会同时屏蔽掉「服务端是否真的接受这个请求体」「CSRF 是否真的被校验」这类问题——**服务端语义只有真跑才验得了**。

### E-09 bash 的工作目录切换会触发写操作安全拦截

- `Set-Location X; New-Item/Copy-Item ...` 被本地安全策略拦截（切换目录后无法验证写入目标）。
- 规避：写文件用绝对路径（`Copy-Item "D:\a" "D:\b"`）或改用文件工具；只读命令不受影响。

### E-10 「把失败降级成空值」是同步/加密代码里最贵的错误处理习惯

- 盲审 P1-1 的根因不是「少了一次校验」，而是 `fetchRemoteProfile()` 把**三种截然不同的状态**（有档案 / 确实没有 / 拿不到）压成了同一个 `null`。
- 压缩掉的那个区分，正是「云端是空的」与「我不知道云端是不是空的」的分界——一旦混淆，后续的写操作就会带着错误的假设执行。
- ⇒ **凡是要据此做写决策的读取，都不该用 `null` 表达多种状态**，应返回可区分的结构（`ok` / `absent` / `error`）。这条对本批的 `fetchRemoteProfile` 直接适用。

### E-11 「变异后测试仍全绿」是判断「零覆盖」最便宜的手段

- 盲审删掉「不覆盖他人档案」的守卫后，**三套测试全部通过**——这条核心安全不变量此前完全没有测试保护。
- 比「读代码觉得覆盖了」强得多，也比「新增一条用例然后它绿了」强得多（后者可能仍是假阳性）。
- ⇒ **对每条安全不变量，都应该问一句：把实现改坏，它会红吗？** 本批据此补了 4 条用例。

### E-12 独立盲审与主会话自查「双向命中同一处」，说明触发路径足够隐蔽

- P1-1（云端档案被覆盖）在盲审运行期间被主会话自查独立发现，盲审随后独立复现并给出实跑证据。
- 两次独立命中同一处 = 这条路径**不是偶然写错**，而是设计上容易被忽略的陷阱（「错误处理降级 + 写操作前置条件」）。
- ⇒ 发现这类问题时，**修复必须同时补上「为什么当初会漏」的防线**（本批的做法是：客户端守卫 + 服务端 409 + 4 条用例 + 报告留痕），否则它会在下一个版本里换个形式回来。

### E-13 「产品隔离」要落到正确的层，否则会与其它产品目标直接冲突

- 原设计让 Focus 与 Muse 各用各的 verification 明文（意图是产品隔离），但档案按**账号**只有一行 ⇒ 后启用的产品永远无法启用，且口令正确也报错误导。
- 本地隔离（不同 storeKey）是对的，必须保留；云端档案隔离则是**与「统一账号共享上下文」相冲突**的。
- ⇒ 设计「隔离」时先问：**要隔离的是哪一层的数据**。把隔离加在错误的层，会制造出比不隔离更糟的故障。
