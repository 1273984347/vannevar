## 3. 设计决策

### 3.1 共享层抽取方式

`shared/vannevar-crypto.js` 导出工厂 `createCryptoModule({storeKey, verificationPlaintext})`，返回 Focus 现有 API 的**同构**实现（`isCryptoEnabled` / `isCryptoReady` / `getCryptoState` / `enableCrypto` / `disableCrypto` / `unlockCrypto` / `lockCrypto` / `encryptData` / `decryptData` / `isEncryptedData`）。

- `products/focus-mvp/crypto.js` 改为薄封装，**导出签名与路径不变** ⇒ Focus 现有 16 + 11 个测试**一行不改**即可继续作为回归基线。
- `products/muse-mvp/core/crypto.js` 新建薄封装，storeKey 用 `vannevar_muse_crypto`，verification 明文用 `vannevar-muse-e2e-verification-v1`。
- 副本落在产品目录内（`focus-mvp/lib/`、`muse-mvp/shared/`），沿用仓库既有「shared/ 为源、产品目录为副本」惯例（`vannevar-context-card.js` / `vannevar-brand.css` 同模式）。

**备选与否决理由**：直接把 Focus 的 `crypto.js` 整份复制到 Muse → 两份 300 行实现分叉，未来修一个加密漏洞要改两处，是更严重的半成品隐患，故否决。

### 3.2 跨设备 salt 同步（A2）

**服务端**：新增表 `user_crypto_profiles`（user_id 主键 + salt / iterations / kdf / verification 密文 / salt 指纹），迁移 `PRAGMA user_version` v11 → v12，幂等 `CREATE TABLE IF NOT EXISTS`。端点挂在既有 `/api/auth/me/*` 下：

- `GET /api/auth/me/crypto-profile` —— 取回本用户的加密档案
- `PUT /api/auth/me/crypto-profile` —— 写入 / 更新

**安全边界**：PBKDF2 salt 是公开参数（不是密钥），可上云；`verification` 只存密文；**passphrase 永不上云、永不落盘**。此点须在 README 与设置页文案中明示，避免用户误解。

**客户端流程**：

1. 启用加密时先 `GET` 云端档案：
   - 云端已有档案 → 复用其 salt 派生密钥，并用云端 verification 反验 passphrase ⇒ passphrase 一致则本地沿用同一 salt（跨设备可解密）；不一致则明确报错「passphrase 与其他设备不一致」。
   - 云端无档案 → 本地生成 salt + verification，并 `PUT` 上云。
2. 每次 push / pull 成功后**幂等** `PUT` 一次本地档案（补齐老用户：老版本本地已有 salt 但云端无档案的情况自动上云）。

**回退**：云端不可达时不阻断同步（加密本身仍生效），仅记录「档案未同步」状态，设置页可手动重试。

### 3.3 Muse 同步加解密语义

- push：明文对象 → `encryptData()` → 密文容器写进 `data`
- pull：读 `data` → `isEncryptedData()` 为真则 `decryptData()`，否则按旧明文处理（**向后兼容，不丢旧数据**）
- 加密已启用但未解锁：抛可读错误并**跳过推送**（不混推明文），沿用 Focus 既有语义

| 风险 | 影响 | 回退方案 |

| 抽共享层破坏 Focus 既有测试 | Focus 回归 | `crypto.js` 路径与导出签名零变化；改完立即跑 16 + 11 |

| 云端档案不可达阻断同步 | 可用性 | 档案同步失败**不阻断**加解密，仅置「未同步」状态 |
