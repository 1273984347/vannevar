### 4.2 关键执行细节

#### ST-01 / ST-02：Bridge 恢复缺陷的定位与修复

**诊断路径**（4 个竞争假设，逐个排除）：

| 假设 | 验证方法 | 结果 |
|---|---|---|
| H1 主库因 WAL 层损坏 | 直连 sqlite3 执行 `PRAGMA journal_mode` | ❌ 排除：页级损坏，与 WAL 无关 |
| H2 备份文件本身损坏 | `integrity_check` 逐个跑 | ❌ 排除：最新备份 = ok |
| H3 WAL 侧车残留导致恢复后被回放写坏 | 合成实验（造 db+wal → 覆盖主文件 → 校验） | ❌ 排除：SQLite 正确忽略 salt 不匹配的 wal，返回 ok |
| H4 覆盖仍被自身连接池占用的 db 文件 | **沙箱内复现** | ✅ **确证** |

**根因（F-05 实测复现）**：`restore_db()` 的流程是「重命名损坏库 → 直接 copy2 覆盖」。重命名在 Windows 上因文件锁失败（`WinError 32`，连接池仍持有句柄）→ 代码走"将直接覆盖"分支 → **覆盖一个仍被打开的、且内容不同的文件，产生不可靠结果**；同时该函数**从不清理属于旧库的 `-wal` / `-shm` 侧车**，也**从不校验备份自身是否完好**（`backups/` 实测混有损坏副本）。

**修复内容**（`backup.py`）：

1. `_file_integrity_ok()` —— 用**独立 sqlite3 连接**校验任意文件（不用全局 engine，避免读到替换前的内容）
2. `_dispose_engine()` —— 动文件**前**先释放连接池，解除 Windows 文件锁
3. `_clear_sidecars()` —— 恢复后清除旧库的 `.db-wal` / `.db-shm`
4. `restore_db()` 重写为 7 步：校验备份 → dispose → 保留损坏库审计副本（rename 失败则 copy2 兜底）→ **复制到临时文件 → 校验临时文件 → `os.replace` 原子替换** → 清侧车 → **独立连接复核**
5. `auto_backup_on_startup()` —— 恢复时**逐个尝试备份**，跳过损坏的（原来只取最新一份，一份坏备份就彻底阻断恢复）
6. `list_backups()` —— 按真实 mtime 数值排序（同秒文件不再排序不稳定）
7. 失败时**回滚**到保留的损坏副本，不让原始文件也丢失

**回归测试**（`tests/test_backup_recovery.py`）锁定 4 个不变量：恢复后必须通过完整性检查 / 必须清除 WAL 侧车 / 坏备份不得覆盖好库 / 不得静默丢失审计副本。

#### 第二轮：独立盲审推翻了我自己的"已修复"结论

盲审在无作者上下文下提出质疑：`test_restore_removes_stale_wal_sidecars` 可能是**假阳性**——断言在恢复动作之前就已成立。实测确认后，挖出两个更深的问题：

1. **SQLite 会顺带删除孤儿 `-wal` / `-shm`**（实测：主库为非 WAL 模式时，`sqlite3.connect` + `close` 之后侧车即消失）→ 集成路径的断言分不清"谁删的"。
2. **实现里存在真实缺陷**：`_clear_sidecars` 的后缀写成 `(".db-wal", ".db-shm")`，拼出 `bridge_mvp.db.db-wal` —— **该函数从未真正清理过任何侧车**；因为 SQLite 的副作用在代劳，测试一直是绿的。

**处置**：
- 修 `_clear_sidecars` 的后缀为 `("-wal", "-shm")`，并加注释说明为何不能写成 `.db-wal`
- 新增 5 条用例把「实现里的分支」变成可观测行为：直接调用 `_clear_sidecars` 的单元测试、spy 验证 `restore_db` **确实调用**了它、定向 monkeypatch 让「临时副本校验」「最终复核」分别失败

| 变异 | 结果 |

#### 对比度门禁的棘轮化（ST-04 延伸）

**问题**：`scripts/check_contrast.py` 对 Bridge 深色「复古档案纸」主题报 3 项不达标 → exit 1 → `qa_all.py`（把 contrast 作为默认门禁步骤）**必然 exit 1** → 开源后 clone 者跑"一键验收"直接见红。

**方案**：引入**已知基线（ratchet）**机制——

- 基线内的 3 项不达标**不阻断**，但照常完整报告并指向 `KNOWN_BASELINE` 清单
- 任何**新增**不达标项**仍然阻断**
- 修复任一基线项后从清单移除，使其重新回到受约束状态

**双向验证**（临时变异→实跑→还原）：

| 变异 | exit | 新增不达标数 | 结论 |
|---|---|---|---|
| A 清空 `KNOWN_BASELINE` | **1** | 3 | 阻断通路有效，且这 3 项确为基线项 |
| B 阈值 4.5 → 9.0 | **1** | 4 | 任意新增项都阻断 |
| C 恢复态（对照） | **0** | 0 | 正常态不误报 |

## 8. 经验沉淀

### E-01 · 「恢复成功」的假象：用独立连接校验替换连接池内校验

- **做对了什么**：恢复流程的最终判定从 `engine.connect()` 改为**独立 sqlite3 连接**，且在复制前后各做一次。
- **为什么有效**：连接池里的连接在恢复期间仍指向"替换前"的文件描述符，用它校验会读到旧内容，从而把"恢复失败"误判或把"恢复成功"误信。
- **适用条件**：任何"替换正在被使用的文件"的场景（数据库恢复、配置热替换、原子更新）。
- **不适用条件**：数据库在内存且无文件后端时，独立连接无意义。
- **复用步骤**：① 校验前先 dispose 连接池 ② 用独立连接读文件 ③ 校验通过后才算成功。
- **量化效果**：本例把「恢复报告成功但结果仍损坏」从 100% 复现变为 0%。
- **证据来源**：`tests/test_backup_recovery.py`（红→绿全过程）。

### E-02 · 原子替换三件套：临时文件 → 校验 → `os.replace`

- **做对了什么**：恢复目标不再直接写 `DB_PATH`，改为写同目录临时文件 → 校验临时文件 → `os.replace` 原子替换 → 失败则回滚到保留的损坏副本。
- **为什么有效**：直接覆盖目标路径时，中途失败会留下半成品且无法回滚；同目录临时文件的 `os.replace` 在 POSIX 与 Windows 上都是原子的。
- **适用条件**：任何"用文件 B 替换文件 A 且 A 可能正在被使用"的场景。
- **不适用条件**：跨卷移动（`os.replace` 不跨文件系统）；需要保留目标 inode 的场景。
- **复用步骤**：写临时文件 → 校验 → `os.replace` → 失败清理临时文件 + 回滚。
- **量化效果**：把"覆盖失败导致目标文件既不是旧版也不是新版"这一类故障降为 0。

### E-03 · "只取最新一份"的恢复策略会被一份坏备份彻底阻断

- **做对了什么**：`auto_backup_on_startup()` 从「取 `backups[0]` 恢复」改为「逐个尝试，跳过损坏的」。
- **为什么有效**：`backups/` 是滚动目录，实测 6 份里 3 份损坏；只取最新一份时，一份坏备份会让整个恢复流程失败——**恢复能力被一份无用备份废掉**。
- **适用条件**：任何有多个候选恢复点的场景（备份轮转、快照列表、候选配置列表）。
- **不适用条件**：候选点数量巨大（>100）时应先做完整性扫描再排序。
- **复用步骤**：① 候选按"最近"排序 ② 逐个尝试 ③ 单个失败不终止 ④ 全部失败才升级为致命错误。
- **量化效果**：本例把"恢复成功率"从"取决于最新一份是否完好"改为"取决于是否存在任一完好备份"。
- **证据来源**：`test_startup_recovery_skips_corrupt_backup_and_uses_next_good`。

### E-04 · 改一个"值"引发的连锁失效，扫描的是"形态依赖"

- **做对了什么**：打包输出从项目外迁到仓内 `dist/` 后，立即扫描并修掉两处引用：`verify_loading.py` 与 `check_links.py`。
- **为什么有效**：这两处不是 import（import 漏了会 ImportError），而是**字符串/路径拼接**——不报错，只在跑起来时暴露。
- **适用条件**：任何改变了"某物的位置"的改动。
- **不适用条件**：纯函数内部的重构（无外部引用）。
- **复用步骤**：① 列出该物的全部引用形态（import / 字符串拼接 / 配置 / CI / 文档）② 改完立刻实跑消费方脚本 ③ 不止查 import。
- **量化效果**：发现 2 处沉默失效，0 处运行时报错。
- **证据来源**：`qa_all.py` 首次实跑报 `verify_loading FAIL`。

### E-05 · 棘轮基线：让"既有不达标"不掩盖"新增不达标"

- **做对了什么**：给 `check_contrast.py` 加 `KNOWN_BASELINE` 清单，基线项照常报告不阻断，新增项阻断。
- **为什么有效**：开源状态下门禁工具"恒红"会让 clone 者误以为项目坏了，也会让维护者忽略真正的红灯。棘轮在**不放水**的前提下恢复了信号。
- **适用条件**：有历史遗留不达标的门禁（对比度、覆盖率、lint、依赖漏洞）。
- **不适用条件**：基线本身不可接受时（应先修再开源）。
- **复用步骤**：① 列出基线项 → ② 基线项单独小节报告 → ③ 阻断只判新增项 → ④ 修复一项删一项。
- **量化效果**：双向验证——清空基线 → exit 1；收紧阈值 → exit 1；恢复态 → exit 0。
- **证据来源**：`scripts/check_contrast.py` 的 `KNOWN_BASELINE` 与变异验证记录。

### E-06 · 资产类文件里的"参赛烙印"只能靠重新渲染清除

- **做对了什么**：先改海报的 **HTML 源文件**，再用 Playwright 重新截图 4 张 PNG，图片里的参赛字样随之消失。
- **为什么有效**：图片里的文字是像素，改 HTML 源文件比用图像工具涂抹更可控、可复现，且源文件与产物永远一致。
- **适用条件**：任何"由可编辑源文件渲染出的位图资产"（海报、截图、图表）。
- **不适用条件**：手工绘制的位图；视频（需 ffmpeg，且本次因缺 ffmpeg 未做）。
- **复用步骤**：找到生成脚本（`scripts/capture_assets.py`）→ 改源 → 重跑生成器 → 校验产物。
- **量化效果**：4 张图去除烙印，源文件与产物保持同步。
- **遗留**：2 个 mp4 未重录（本机无 ffmpeg）。

### E-07 · 品牌资产里的第三方声明，要与"实际入库清单"核对而非与"生成清单"核对

- **做对了什么**：`NOTICE` 声明 `sql-wasm.js/.wasm` 为第三方，`frames-extended/` 为项目自有素材；迁移后核对主仓实际入库清单，确认 `frames-extended/` 已不在主仓，并在 archive 仓单独出具归属说明。
- **为什么有效**：声明与实际入库内容脱节时，GitHub 的自动扫描与人工核查都会给出错误结论。
- **适用条件**：任何含第三方代码/素材的开源仓库。
- **不适用条件**：纯自研无第三方依赖的仓库。
- **复用步骤**：打包后用 `git ls-files` 核对 NOTICE 提到的每一项是否真的在库里。

### E-08 · 底层库的「顺带行为」会掩盖你的显式清理逻辑，让测试变成假阳性

- **做对了什么**：独立盲审指出 `test_restore_removes_stale_wal_sidecars` 可能是假阳性；实测确认后做了**对照实验 + 反向实验**，最终定位到两个问题：
  1. **SQLite 在打开数据库时会顺带删除同目录的孤儿 `-wal` / `-shm`**（实测：主库为非 WAL 模式时，`sqlite3.connect` + `close` 之后侧车即消失）。因此任何「经由 restore_db 的间接路径」的断言，都分不清侧车是被本项目代码删的，还是被 SQLite 的副作用删的。
  2. **实现里存在真实的路径拼接错误**：`_clear_sidecars` 的后缀写成了 `(".db-wal", ".db-shm")`，拼出的是 `bridge_mvp.db.db-wal` —— **该函数从未真正清理过任何侧车**，且因为 SQLite 的副作用，测试一直是绿的。
- **为什么有效**：这条缺陷能一路逃过「测试全绿 + 盲审通过」两道关，靠的是**底层库恰好做了同样的事**。只有主动构造「库里没有、只有你打算删的东西」并**直接调用被测函数**，才能把责任归属钉死。
- **适用条件**：任何实现了「清理临时文件 / 侧车文件 / 缓存文件」的代码，尤其当底层库或操作系统**也会顺手清理同名文件**时（SQLite 的孤儿 WAL、Windows 的临时目录清理、Git 的 gc）。
- **不适用条件**：被清理对象有且仅有本代码一个清理者，且清理行为可通过外部观测唯一确定。
- **复用步骤**：
  1. 先查底层库是否对该类文件有「顺带清理」行为（读文档 + 最小实验）；
  2. 用**直接调用被测函数**的单元测试锁住它，不要只靠集成路径；
  3. 用 **spy / 定向 monkeypatch** 把「实现里的某个分支」变成可观测行为（例：记录 `_clear_sidecars` 是否被调用；让「对临时副本的校验」返回 False）；
  4. 做**反向验证**：故意破坏实现的每个关键分支，确认对应测试变红——**变不红的分支就是没被覆盖的分支**。
- **量化效果**：本次反向验证矩阵从「1/6 分支被覆盖」提升到「6/6 被覆盖」；过程中额外发现并修复了一个**从未生效的清理逻辑**。
- **证据来源**：`tests/test_backup_recovery.py`（12 用例）+ 6 组变异注入实验。

### E-09 · 反向验证脚本本身也要被验证：每条变异必须断言「确实生效」

- **做对了什么**：第一版反向验证脚本在 B/C/D 三条变异上给出「测试未覆盖」的结论，但事后发现其中**至少一条变异的替换串根本没匹配上原文**——即变异没生效，测试当然全绿。补上「若 `old not in orig` 则直接报错」的断言后，结论才可信。
- **为什么有效**：反向验证的失败结论，本质是「变异生效了但测试没抓到」；如果变异压根没生效，「测试没抓到」就是**假阴性**，会把好好的实现误判成没覆盖。
- **适用条件**：任何用「文本替换注入故障」做变异测试的场景。
- **不适用条件**：通过 mock 框架注入故障（替换是否生效由框架保证）。
- **复用步骤**：① 每条变异先断言 `old in original`；② 变异后断言 `mutated != original`；③ 跑完必须还原原文件（用 `finally`）；④ 输出里区分「变异未匹配」与「测试未覆盖」两种状态。
- **量化效果**：避免把 3 条无效变异误报为「未覆盖」，避免据此做出错误的「测试无用」判断。
- **证据来源**：反向验证脚本 v2 → v5 的迭代记录。

### E-10 · 依赖锁定版本与本机实际版本不一致时，测试结论对 CI 的外推性是未验证项

- **做对了什么**：盲审实测发现本机环境与 `requirements.txt` / `requirements-dev.txt` 的锁定版本有 3 处不一致（`httpx` 0.27.2 vs 0.28.1、`pydantic` 2.12.3 vs 2.12.5、`pytest` 9.1.1 vs 8.4.2）。尝试建独立 venv 安装锁定版本复跑以消除该不确定性，因 **PyPI 网络读超时**未能完成。
- **为什么有效**：测试结论的可信度不只取决于「跑没跑过」，还取决于「在什么依赖组合下跑的」。CI 会用锁定版本，与本机不同则结果可能不同——这是**证据的适用边界**，必须显式标注而非默认忽略。
- **适用条件**：任何把「本地实跑通过」当作「CI 会通过」依据的仓库。
- **不适用条件**：仓库无锁定版本（纯 `>=` 约束）且 CI 与本地解析结果必然一致。
- **复用步骤**：① 对比 `pip list` 与锁定文件，列出差异项；② 若差异项涉及测试框架或被测库的关键路径，标注为未验证项；③ 有网络时用独立 venv 复跑消除不确定性；④ 无网络时在报告与 CI 注释中写明该限定条件。
- **量化效果**：把「CI 必然绿」的隐含假设降级为「本地实测绿，CI 等价性待验证」。
- **证据来源**：盲审实测的版本对比 + venv 安装网络超时记录。

### E-11 · `URL.pathname` 是 Windows-only 写法，只有 Linux CI 能暴露

- **做对了什么**：GitHub Actions 首跑（ubuntu-latest）报
  `Cannot find module '/home/runner/.../focus-mvp/home/runner/.../focus-mvp/crypto.js'` —— 路径被重复拼接。定位到测试里的写法：
  `path.dirname(new URL(import.meta.url).pathname.replace(/^\//, ''))`
- **为什么有效（且为什么本地测不出）**：`URL.pathname` 在 Windows 上是 `/C:/...`（**需要**剥掉前导 `/` 才是可用的绝对路径），在 Linux 上则是本来就带前导 `/` 的绝对路径（剥掉就变成相对路径）。于是同一行代码：
  | 平台 | `pathname` | 剥 `/` 后 | `path.resolve` 结果 |
  |---|---|---|---|
  | Windows | `/C:/repo/tests/t.mjs` | `C:/repo/tests`（绝对 ✓） | `C:\repo\crypto.js` ✓ |
  | Linux | `/home/runner/.../tests/t.mjs` | `home/runner/.../tests`（**相对** ✗） | `<cwd>/home/runner/.../crypto.js` ✗ |
  同一个值在两个平台被剥掉 `/` 的后果完全相反。**本地 Windows 上 Node 22 与 Node 24 都是 16/0 通过**，只有 Linux 环境暴露。
- **修法**：用 Node 官方 `fileURLToPath(import.meta.url)`（平台正确；在 Windows 上遇到 Linux 路径会**直接抛错**而非静默错位）。同仓的 Muse 测试与 loader 本来就是这么写的 —— **同一仓库里两种写法并存，是最强的信号**。
- **适用条件**：任何用 `new URL(import.meta.url).pathname` 手工还原文件路径的 ESM 代码（Node 脚本、测试、构建工具）。
- **不适用条件**：浏览器环境（没有 `node:url`），此时应直接用 `import.meta.url` 交给浏览器解析。
- **复用步骤**：① grep `import.meta.url` 找所有 `.pathname` 用法；② 换成 `fileURLToPath`；③ **在 CI 里用 Linux 跑一遍**（本地 Windows 无法覆盖）。
- **量化效果**：CI 首跑从「Extensions job 失败」变为全绿；同一类隐患在全仓清零（Muse 侧本就正确）。
- **证据来源**：GitHub Actions run `40173286394` 失败日志 + 本地 Linux 路径语义复现实验。
